# Current Hermes research for the proposed Aphrael contract

Research date: 2026-09-14. Official upstream inspected at commit **49c6d4a9e0dddc64d6333c5b1fcc9d911463a8fd** in a read-only research checkout. This is source/documentation research, **not installation or execution proof**. No auth store or raw credentials were inspected. Findings below cover installation, providers, extension/security surfaces, delegation/processes, UI/API, skills and MCP; profile/distribution/state/Kanban design is separately evaluated in the contract.

All relative source links below are pinned to that inspected official commit.

## Native Windows and interactive surfaces

The [native Windows guide](https://github.com/NousResearch/hermes-agent/blob/49c6d4a9e0dddc64d6333c5b1fcc9d911463a8fd/website/docs/user-guide/windows-native.md) documents Windows 10/11 without WSL, containers, or administrator rights. Official scripts/install.ps1 supports -Commit, -Tag, -SkipSetup, -HermesHome and -InstallDir. Its managed bootstrap supplies uv/Python, Node, PortableGit as necessary; reuse it rather than duplicate dependency logic. Default code is under %LOCALAPPDATA%/hermes/hermes-agent, default state root %LOCALAPPDATA%/hermes. Installer sets user PATH/HERMES_HOME; fresh-shell behavior must be tested.

Native terminal tools use Git Bash. This is native Windows operation, not a Linux prerequisite. CLI/TUI, gateway, cron, browser, MCP and most dashboard functions are documented as supported. Dashboard embedded /chat terminal is specifically unsupported on native Windows (POSIX PTY requirement); do not select that as the required chat surface.

[Desktop](https://github.com/NousResearch/hermes-agent/blob/49c6d4a9e0dddc64d6333c5b1fcc9d911463a8fd/website/docs/user-guide/desktop.md) uses its own hermes serve backend and tui_gateway JSON-RPC/WebSocket API, not a mandatory separate dashboard. It shares CLI installation/state, supports profiles and hermes desktop --cwd. [CLI profile pre-parser](https://github.com/NousResearch/hermes-agent/blob/49c6d4a9e0dddc64d6333c5b1fcc9d911463a8fd/hermes_cli/main.py) recognizes --profile/-p. An explicit Aphrael profile launch through stock Desktop or TUI is preferable to a custom frontend. The exact installed-version command and profile selection still require real Windows validation. Voice must not block this path.

[API server](https://github.com/NousResearch/hermes-agent/blob/49c6d4a9e0dddc64d6333c5b1fcc9d911463a8fd/website/docs/user-guide/features/api-server.md) is a separate supported OpenAI-compatible gateway surface; /v1/chat/completions is stateless and receives full message history. It is not required for this milestone.

## Codex OAuth and routing

[Official auth implementation](https://github.com/NousResearch/hermes-agent/blob/49c6d4a9e0dddc64d6333c5b1fcc9d911463a8fd/hermes_cli/auth_codex.py) supports existing Hermes OAuth reuse, then an optional valid unexpired Codex CLI credential import, otherwise device-code login. _import_codex_cli_tokens resolves CODEX_HOME or ~/.codex, reads through Hermes itself, and never writes the source CLI file. _login_openai_codex offers import (default no, separate login recommended) and configures provider openai-codex. It must be invoked through supported Hermes login/model UX, not by Aphrael copying credential files or importing private helpers. Actual current-account usability is unknown until authorized implementation executes a real model turn.

Do not confuse this provider login with [hermes import-agent codex](https://github.com/NousResearch/hermes-agent/blob/49c6d4a9e0dddc64d6333c5b1fcc9d911463a8fd/website/docs/user-guide/import-from-other-agents.md): that migrates instructions/skills/MCP configuration and expressly never reads credential files. Bulk importing the user's unrelated Codex configuration is unnecessary.

[Auth state implementation](https://github.com/NousResearch/hermes-agent/blob/49c6d4a9e0dddc64d6333c5b1fcc9d911463a8fd/hermes_cli/auth.py) supports per-provider read-only fallback to global-root auth in profile mode. Profile isolation must therefore state intentional credential inheritance instead of assuming profiles have no shared credentials. [Auxiliary routing configuration](https://github.com/NousResearch/hermes-agent/blob/49c6d4a9e0dddc64d6333c5b1fcc9d911463a8fd/website/docs/user-guide/configuration.md) accepts main/codex/registry providers; explicitly use the authorized provider for auxiliaries and avoid silent model/service fallback. No new paid service is required by this researched architecture.

## Plugins, hooks and approval boundaries

[Plugins](https://github.com/NousResearch/hermes-agent/blob/49c6d4a9e0dddc64d6333c5b1fcc9d911463a8fd/website/docs/user-guide/features/plugins.md) provide tools, lifecycle hooks, provider extensions, slash commands and approval transports. General plugins default disabled until plugins.enabled authorizes them. Consent/safe mode can prevent loading; installation alone does not prove a guardrail is active. [Plugin SDK](https://github.com/NousResearch/hermes-agent/blob/49c6d4a9e0dddc64d6333c5b1fcc9d911463a8fd/website/docs/developer-guide/plugins/index.md) documents persistent plugin storage and dispatch_tool through the ordinary approval/redaction/budget path. Use supported imports: old internal module aliases become unloadable from 2026-09-14, a specific compatibility risk at this research date.

[Hooks](https://github.com/NousResearch/hermes-agent/blob/49c6d4a9e0dddc64d6333c5b1fcc9d911463a8fd/website/docs/user-guide/features/hooks.md) distinguish:
- pre_tool_call can block, require human approval, or rewrite arguments; approve means escalation, never permission bypass.
- Python callback exceptions are logged/skipped. pre_tool_call timeouts fail closed, but that is not a blanket exception-fail-closed guarantee.
- Shell pre_tool_call hooks default fail open; explicit fail_closed: true blocks spawn failures, timeouts, nonzero/malformed responses. A valid empty object is still a no-op.
- Kanban lifecycle hooks are observer-only and cannot veto completion. Post-tool observations and summaries are not independent proof.
- Approval transports only decide where a human prompt appears; they are not authorization-policy APIs.

[Security](https://github.com/NousResearch/hermes-agent/blob/49c6d4a9e0dddc64d6333c5b1fcc9d911463a8fd/website/docs/user-guide/security.md) defaults approvals.mode to smart (auxiliary-model auto-decisions). Aphrael should explicitly evaluate manual with cron_mode, single_query_mode and unattended_mode set to deny. No YOLO or globally autoapproved dangerous host actions. File safe-root/denylist protections apply to write_file/patch only; terminal commands execute as the same OS user and can bypass these paths. Skills, profiles, prompts and these local guards must not be represented as a hostile-worker sandbox.

The smallest evidence extension should use supported tools/hooks/review and explicit observable postconditions. It must test absent/disabled/crashed hooks, false worker claims and failed actions. Startup checks and known-action evidence cannot prove universal shell containment. The contract must not claim observer hooks can enforce all state transitions.

## Delegation and background processes

[Delegation](https://github.com/NousResearch/hermes-agent/blob/49c6d4a9e0dddc64d6333c5b1fcc9d911463a8fd/website/docs/user-guide/features/delegation.md) documents fresh child conversations, separate terminal sessions, inherited tool access, top-level asynchronous handles and completion messages. Parent conversation can continue. Fresh does not mean OS-isolated: children receive workspace context (.hermes.md/AGENTS chain etc.; SOUL excluded) and share host files. Parent must supply task constraints. Child background processes are terminated when the child closes; a returned PID does not transfer ownership.

Structured output_schema validates answer shape and gives one correction turn; it does not verify facts. Completion delivery acknowledgment means admitted into a queue/timeline, not completed model response or verified external action. API async completions add a durable timeline delivery row; the API client owns the next model turn.

[Delegate implementation](https://github.com/NousResearch/hermes-agent/blob/49c6d4a9e0dddc64d6333c5b1fcc9d911463a8fd/tools/delegate_tool.py) and [process registry](https://github.com/NousResearch/hermes-agent/blob/49c6d4a9e0dddc64d6333c5b1fcc9d911463a8fd/tools/process_registry.py) show background dispatch and checkpointed process/notification metadata. Recovered detached host processes lack output history and, when no waitable handle survives, an exited process has unknown exit code (None). PID liveness is not task success. Ephemeral delegated execution is not a replacement for Kanban durable work; real restart/recovery behavior needs the contract's Windows acceptance demonstration.

## Skills and MCP

[Skills](https://github.com/NousResearch/hermes-agent/blob/49c6d4a9e0dddc64d6333c5b1fcc9d911463a8fd/website/docs/user-guide/features/skills.md) are agentskills.io-compatible on-demand documents with progressive disclosure and slash invocation. They can include supporting scripts/resources. Local profile skills are primary; external skill directories are supported. Profiles can opt out of bundled skills. Port Strategerium/Necroneerium as explicit specialist workflows with their role prompts and real paths, replacing Codex-specific tool names only where necessary; do not claim copied text alone exercises their delegation/review requirements. Runtime-managed skills can mutate, so distribution update ownership must be explicit.

[MCP](https://github.com/NousResearch/hermes-agent/blob/49c6d4a9e0dddc64d6333c5b1fcc9d911463a8fd/website/docs/user-guide/features/mcp.md) supports stdio and HTTP, discovery, resource/prompt wrappers and per-server tool filtering through mcp_servers in profile config. Standard installation includes support; optional catalog servers are disabled until installed. Use no extra MCP service without an actual Aphrael requirement. MCP results remain untrusted data; credentials belong outside Git.

## Profile distribution, identity, state and Kanban (coordinated upstream inspection)

The root researcher's inspection of [profile_distribution.py](https://github.com/NousResearch/hermes-agent/blob/49c6d4a9e0dddc64d6333c5b1fcc9d911463a8fd/hermes_cli/profile_distribution.py) identified a material documentation/implementation boundary: absent an explicit files allowlist, payload discovery can include the whole source tree minus exclusions. Use an explicit distribution payload allowlist; never assume only identity/config/skills are selected. Distribution-owned directories are replaced recursively on update. User config is preserved by update, whereas forced install resets config. Therefore mutable user skill/plugin additions must not be placed inside replace-owned directories without a tested preservation mechanism. Local distribution source is supported and records its absolute provenance; URL clone uses depth one and has no separate revision argument in the inspected path. Pin the implementation checkout/release deliberately and test the actual supported update path.

[Profiles](https://github.com/NousResearch/hermes-agent/blob/49c6d4a9e0dddc64d6333c5b1fcc9d911463a8fd/website/docs/user-guide/profiles.md) have separate homes and warn about a single agent writer per home. [Memory](https://github.com/NousResearch/hermes-agent/blob/49c6d4a9e0dddc64d6333c5b1fcc9d911463a8fd/website/docs/user-guide/features/memory.md) stores MEMORY.md and USER.md under memories/, frozen into the prompt at session start; prove persistence by opening a genuinely new session. [Context files](https://github.com/NousResearch/hermes-agent/blob/49c6d4a9e0dddc64d6333c5b1fcc9d911463a8fd/website/docs/user-guide/features/context-files.md) distinguish profile-root SOUL identity/tone from repository development instructions, with .hermes.md highest project priority. Do not bury authorization or correctness guarantees only in SOUL.

[Kanban implementation](https://github.com/NousResearch/hermes-agent/blob/49c6d4a9e0dddc64d6333c5b1fcc9d911463a8fd/hermes_cli/kanban_db.py) has complete_task transitions from ready/running/blocked/review to done. The PR acceptance gate applies only to its specific configured contracts; absent such a contract it does not provide general external-outcome verification. Completion lifecycle hooks run after commit. Native review is useful but cannot be described as a universal proof gate. Kanban home is shared-root by default with HERMES_KANBAN_HOME override; named boards are a separate scope, and missing/mistyped selection may fall back to the default board. The Aphrael contract must explicitly bind and validate the intended board/state path and exercise false-success, recovery and review tests, rather than assuming a named assistant profile isolates every Kanban operation.

## Required interpretation

These findings support a Hermes profile/distribution architecture with narrow Aphrael extensions, not a parallel generic runtime. They do not certify this workstation, provider account, approved-plugin loading, native process recovery, Desktop startup or Kanban verification. Those remain real execution gates after Clifton approves the reviewed contract. No implementation, provider login, install or integration test was performed for this research.
